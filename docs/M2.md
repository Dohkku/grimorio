# M2: organizing

M1 left a program that opens and shows the library. M2 is the one that lets you
**change it**: tags, notes, trash, batch editing and an undo that covers all of
the above.

The gate was «tag 10,000 items without freezing the interface». It comes in at
**344 ms**, with the grid scrolling at 133 fps and two dropped frames out of the
forty-four the operation lasts.

## Undo is implemented once

The rule was written in the plan from the start: *undo is implemented once, in
the bus, and covers every operation*. The piece that makes it happen is
`Parche`.

A patch says which fields of an item are touched (rating, tags, folders, note,
name, trash), and a `None` means «leave this alone», never «set this to empty».
Applying it returns **the opposite patch**: the previous values, and only for
the fields that really changed.

```rust
let atras = Parche::estrellas(5).aplicar(&mut item);
// atras.estrellas == Some(2), and applying it leaves the item as it was
```

Everything else follows from there. An operation is one list of `(id, parche)`
going forward and another going back; undo applies the backward one and redo
the forward one. No operation writes its own inverse by hand, which is where
these systems break without anyone noticing.

Folders are the exception, on purpose: for those the **whole** tree is stored
before and after. It is a few dozen rows, and the hand-written inverse of
«delete a folder with three children» is exactly the kind of code that fails on
the day nobody is looking. Deleting a folder and unhooking its items are a
single operation: a half undo (the folder comes back, but empty) would be worse
than not being able to undo.

The opposite of importing fifty files is sending them to the trash, never
deleting them. Undo should never be able to lose a file.

The stack lives in memory and dies with the program. An undo that survives
closing promises more than it can keep: between one session and the next, the
`item.json` files may have changed from outside.

## Saving ten thousand things

M1's batch editing saved items one at a time, and each `save_item` was a SQLite
transaction. Tagging ten thousand meant ten thousand transactions.

Now it is done in batches of 512: the `item.json` reads and writes in parallel
(lots of small files, which is exactly what a modern disk does better at once
than in a queue) and **a single transaction per batch**.

| 10,000 items | one at a time | in batches |
|---|---|---|
| tag | 49.1 s | **1.2 s** |
| undo it | 10.5 s | **889 ms** |

Forty times faster. And along the way one `SELECT` per item went away: passing
`None` to `upsert` keeps whatever thumbnail was already there, because the
statement uses `COALESCE`. Asking for the pack offset beforehand changed
nothing.

An unreadable `item.json` **does not abort the batch**: it is counted separately
and the batch carries on. With ten thousand items, leaving half of them
half-done because of one broken file is worse than finishing and reporting it.

## What shows on screen in the meantime

Tagging ten thousand does not block the interface because the work is on the
core thread, but that alone is not enough: a window that responds and says
nothing also looks frozen. The budget being measured is **the gap between two
progress updates**, rather than the total time: median 56 ms, worst 114 ms,
against a cap of 250 (which is roughly where an interface starts to look dead).

And a new rule that fixed a real bug: **a change only rebuilds the view if it
can take the item out of what is being looked at**.

```rust
t.papelera
    || (t.carpetas && q.folder.is_some())
    || (t.etiquetas && (!q.tags.is_empty() || q.text.is_some()))
    || (t.estrellas && (q.min_stars.is_some() || ...))
```

Without this, undoing a star rating with a hundred thousand items cost a whole
query (eighty-five milliseconds) just because the undo menu had asked for it.
With it, one cell is repainted. And the other way round: removing the fourth
star inside an `estrellas:>=4` filter **does** rebuild the view, because leaving
the photo there would be showing a lie.

## The trash

A field in `item.json`, with no files being moved. That makes undoing it
instant and independent of the disk cooperating, and a trashed item keeps its
tags and folders in case it comes back.

You see either the library or the trash, never both mixed: a trashed item that
reappears among the others is the quickest way to lose trust in a program.

Emptying it does delete for real, and that is why it **throws away the whole
history**: leaving the menu offering «undo» after deleting files would be a
lie. The one thing it does not reclaim is the thumbnails' space inside the
pack, which is written by appending at the end and only shrinks when compacted;
a gap costs a few kilobytes and compacting costs rewriting the whole file.

## The search bar understands what you type

```
tipografía etiqueta:rótulo estrellas:>=4 peso:>2mb orientacion:vertical
```

It exists instead of a panel with fifteen dropdowns for a concrete reason: a
panel is walked with the mouse and has to be walked all over again to change
one thing; a line of text can be edited, copied, pasted and (the day smart
folders exist) **is** the smart folder.

Rules that earned their test:

- **Whatever is not understood is text.** Pasting `https://ejemplo.com/foto.png`
  searches for those words instead of throwing an error about the `https`
  field. A search bar that punishes you for typing is a search bar nobody uses.
- **A half-typed field is not an error.** `etiqueta:` with nothing after it is
  someone typing.
- **A value that is not understood gives a warning, but searches anyway.**
  `estrellas:muchas` leaves a message in the status bar and searches for
  «muchas» as a word.
- `>4` and `>=5` are the same thing for integers, so there is only one way of
  saying it once it reaches the SQL.
- `#rótulo` is the same as `etiqueta:rótulo`, because it is quicker to type.

The mouse filter panel **writes to that same line** and reads from it. There are
no two truths that can disagree, and it is also the only way someone learns the
language: they click «≥4» and see `estrellas:>=4` appear.

## What was hard to find

**When filtering, cells showed another item's photo.** The worst of all, and it
came from M1 without anyone noticing: the URL of each thumbnail was
`image://grim/<position in the grid>`, and Qt's image cache is keyed by URL.
Filtering the library left cell 4 serving the thumbnail of whatever held
position 4 in the previous view. It looked like boxes with one photo's aspect
ratio and another's image inside, and only when changing filters (which was
barely done before M2). Now the URL carries the **item id**, which also lets
the cache survive a filter change: going back to a previous search no longer
decodes anything.

**Enter applied the tag from the list instead of the one typed.** The
autocompletion left the first suggestion highlighted, so typing a new tag that
starts like an existing one («rótul» with «rótulo» in the list) was impossible.
Now nothing is preselected: the arrows choose, and plain typing writes what you
type.

**The ratings on selected cells cost twenty-eight frames.** In a pass with ten
thousand selected there were 33 frames above 16.6 ms; without that decoration,
6. Outlined text is expensive and it was instantiated in every visible selected
cell. It also got in the way: a selection of ten thousand with a row of stars
on every cell stops letting you see the photos. Now they show on hover, and on
the selection only if it is a handful (the same number, 64, that the bridge uses
to decide whether to report items one by one).

**Redoing the layout left the grid blank for an instant.** `recalcular` emptied
the slots and waited for the view to ask again; each visible cell lost its
image, asked for it again and made its entrance all over again. A flicker of
the whole grid every time something changed in a batch. Now it is spread over
the window that was already being looked at, and since the spread compares slot
by slot, if the geometry did not change nothing is reported.

**The sidebar's «All 100,000» kept the number from startup.** You trashed three
items and it still said a hundred thousand. The total now travels with the
folder tree, which is where it is painted and what makes it change.

**`Locale` does not exist inside a `.pragma library`.** The date in the
inspector threw a `ReferenceError` per frame. The script caught it.

**Buttons inside a `Flow` complained on the console on every repaint.** `Flow`
positions its children and an anchor gets in the way. The button now carries
centering as a property that can be turned off.

**The empty grid message showed the raw filter.** With the trash empty it said
«nothing matches «papelera:si»». Now there are three messages: an empty trash is
good news, an empty library is an invitation, and only a search with no results
deserves repeating what was searched for.

**The batch benchmark left ten thousand items tagged** and the next run measured
something else. Now it undoes itself when it finishes, just like the script.

## Numbers

100,000 items, 180 Hz monitor, a twelve-second automatic pass with a batch of
10,000 launched at the one-second mark.

| | value |
|---|---|
| tag 10,000 (end to end) | **344 ms** |
| select 10,000 | 16–21 ms |
| frames during the batch | 44 |
| of those, above 16.6 ms | **2** |
| worst frame of the batch | 36–38 ms |
| mean over the whole pass | 7.4 ms (134 fps) |
| above 16.6 ms in 12 s | 6–9 of 1,600 (0.4 %) |

Without a batch, the pass stays the same as in M1: 10.0 ms mean (100 fps), p95
of 13.5 ms. The viewer stays within budget: p50 1.5 ms, p95 6.2 ms against a
budget of 120.

## How this is reviewed without a person in front of it

```sh
grimorio BIBLIOTECA --guion /tmp/paso-      # walks the interface and captures each step
grimorio BIBLIOTECA --bench 12 --lote 10000 # batch editing with the grid moving
grim bench batch --n 10000                  # the same without a window, with a budget
```

The script now walks the twenty-one steps of M2 (batch tagging, autocompletion,
filtering by a tag, note, folder, viewer, trash, delete confirmation, filter
panel) and **cleans up after itself with undo**: if the stack got the order
wrong, the library would not end up as it was and the next run would give it
away.

## Status

- **135 Rust tests**: 93 for the core (including 11 for the log, 14 for the
  filter language and 9 for editing, trash and undo), 25 for the bridge, 4 for
  the CLI and 13 for the wgpu spike.
- 3 on the Qt side: the grid geometry, the sentinel for hand-written colors and
  a clean `qmllint`.

## What M2 leaves out

- Smart folders: they are a saved query, and the query is already written on a
  single line. Saving it is what is missing. M3.
- Duplicates, watched folders, color search from the window (the core already
  does it; the picker is missing).
- Video, PDF, RAW, fonts: M3.
