# M1: the application

What M0 left behind was a core with a command line and two grid mockups. M1 is
the program: a window that opens, shows the library, lets you organize it and
does not choke on a hundred thousand items.

```sh
grimorio ~/Referencias.grimorio
```

## The three layers, and why the middle one exists

```
grimorio-core   (Rust)   library, index, import, thumbnails
      ↑
grimorio-puente (Rust)   own thread · command bus · immutable views
      ↑  C ABI
app             (C++/QML) window, grid, folders, inspector, viewer
```

The bridge has **two paths, deliberately different**:

- **The command bus.** JSON in both directions, asynchronous, on the single
  thread that owns the `Library`. It is low frequency: these are the actions of
  a person. Being JSON makes it inspectable and easy to fake in a test, and it
  leaves the door open for a plugin to speak the same language without
  inventing a second protocol.
- **The hot path.** The grid reads the published view by index, with no copies
  and no serialization: the bytes of a thumbnail are a pointer inside the
  memory-mapped pack. Two hundred cells per frame do not fit through a channel.

And one rule that holds the rest up: **the view is immutable**. The core thread
does not modify it; it builds a whole new one and swaps it in. Whoever paints
takes a counted reference and releases it when done, so a slow query never
leaves the grid half-painted or pointing at memory that is gone.

## Folders

A folder in Grimorio is **a tag with a hierarchy**. The file does not live in
it. An item can be in several at once, and dragging a selection onto the sidebar
**adds** instead of moving.

The truth is split between two places, on purpose:

- `folders.json` stores which folders exist (name, parent, color, order).
- each `item.json` stores which ones that item is in.

That way, deleting `index.sqlite` loses nothing, and copying an item to another
library carries its membership inside the file itself.

Clicking a folder also shows what is in its children, which is what someone
coming from a file manager expects. In SQL this is solved with a
`WITH RECURSIVE` and a `UNION` (not `UNION ALL`): if someone edits
`folders.json` by hand and leaves a cycle, the query gives an odd result instead
of hanging.

Deleting a folder **does not delete its items**. Removing a tag does not throw
away the photo.

## The grid

It is not a `GridView`. `GridView` only does equal cells, and justified rows
(each image with its own aspect ratio, the whole row filling the width) are half
of why a reference gallery is pleasant to look at.

It is a `Flickable` with a home-made layout and a **ring of slots**: each visible
cell lands in `indice % ranuras`, and since visible cells are always a
contiguous range, two never collide as long as there are slots to spare. The
delegate is neither created nor destroyed while scrolling; its properties
change, which is the cheap part.

The geometry lives in `app/src/filas.h`, with no Qt Quick and no model, and has
eleven tests of its own. It is kept apart because it is the part of the
interface where a bug does not fail loudly: it gives a slightly crooked grid,
and those are the ones that stay around for months. One of the tests is a
budget: redoing the layout of a hundred thousand items has to fit in one frame,
because it is redone on every pixel while the window is resized.

## Numbers, with the whole program loaded

100,000 items, 180 Hz monitor, automatic pass: the whole library top to bottom
and back in twelve seconds. It is far more brutal than any human scroll.

| | square grid | justified |
|---|---|---|
| mean | **7.64 ms** (131 fps) | 10.64 ms (94 fps) |
| p50 / p95 / p99 | 7.56 / 9.68 / 10.76 ms | 10.70 / 13.68 / 17.78 ms |
| above 16.6 ms | 1 of 1,520 (0.07 %) | 2 of 1,100 (0.18 %) |
| worst frame | 45 ms, **at 0.1 s** | 49 ms, **at 0.1 s** |
| first frame | 372 ms | 419 ms |
| own memory | 216 MB | 236 MB |

The worst frame always falls in the first tenth of a second: it is startup
(first layout and first batch of textures), not a stutter while working.

Opening the viewer full screen, twenty-four times spread across the whole
library:

| | measured | budget |
|---|---|---|
| p50 | **1.6 ms** | — |
| p95 | **7.0 ms** | 120 ms |
| maximum | 13.2 ms | — |

The viewer first paints the dominant color, then the 320 px thumbnail that is
already decoded, and on top of that the 1024 px preview when it arrives. There
is never an empty rectangle waiting for the disk. (The measurement is with the
system page cache warm; cold, the first opening reached 227 ms.)

## What was hard to find

**The grid came out blank with the delegates created and the images decoded.**
`recalcular` emitted the geometry signal **before** emptying the slots. The view
responds to that signal by calling `mirar` right away, so `recalcular` itself
erased exactly what had just been placed. A bug spanning two lines.

**Binding `sourceSize` to the size of each cell looked like a saving and was the
opposite.** Qt's cache is keyed by (image, requested size). In justified mode
each row has a different height, so the same thumbnail was decoded again row
after row: 139,768 decodes in one pass. Without requesting a size it drops to
94,976, but each texture becomes 320 px and what shoots up is the upload to the
GPU. The answer is a single size for the whole grid, bound to the target size:
131 fps in the square grid, the same as `GridView` gave.

**Setting a star rating did not show.** The published view predates the change,
so announcing "item X changed" without saying to what left the star invisible
until the next query (and querying the whole library again costs eighty-five
milliseconds per keypress). Now the event carries the new state inside and the
model applies it on the fly. Above sixty-four items it stops announcing them one
by one, sends progress and republishes the view a single time at the end: a
hundred thousand events would drown the interface thread.

**Five stars where there were four.** Inside a delegate, `parent` is not always
what it seems. The same pattern was in the keyboard shortcuts, where the bug
would have been the 3 key setting something else. Both now use an `id` of their
own.

**`inspector.width` bound to `modelo.seleccion.length`** built the whole list
of identifiers on every evaluation of that expression. With a hundred thousand
selected, a hundred thousand strings per repaint. Now there is a property that
only counts.

**The inspector said "nothing selected" with "1 selected" right next to it.**
When the filter changes, the focused item may not be in the new view while
others from the selection are. Now focus falls on the first one that survives.

**Opening the inspector narrowed the grid little by little**, and the grid redoes
its layout with every width change. Now the space is given up all at once and
what is animated is the inspector sliding over the gap: it looks just as smooth
and costs a single layout.

**The script left a folder behind on every run**, so the next one measured
something else. Now it cleans up what it creates.

## How this is reviewed without a person in front of it

```sh
grimorio BIBLIOTECA --guion /tmp/paso-      # walks the interface and captures each step
grimorio BIBLIOTECA --bench 12              # automatic pass and statistics
grimorio BIBLIOTECA --visor 24              # how long the viewer takes to show
grimorio BIBLIOTECA --captura a.png         # one frame and exit
```

Script mode is more than a demo: it selects, sets ratings, creates a folder,
puts items in it, filters, opens the viewer, searches and switches layout,
leaving a screenshot of each step. It is what found five of the bugs above.

## Status

- **66 Rust tests** (59 for the core, 4 for the CLI, 18 for the bridge) and
  **13 for the wgpu spike**, plus three on the Qt side: the grid geometry
  (eleven cases), the sentinel for hand-written colors and a clean `qmllint`.
- None needs a desktop except the screenshots.

## What M1 leaves out, on purpose

- Opening or creating a library from the window: for now it is passed as an
  argument or through `GRIMORIO_LIB`. Creating one is done with `grim init`.
- Undo. It belongs to M2 and has to be done properly, with a log, not with a
  patch.
- Trash, notes, tag autocompletion, smart folders: M2.
- Video, PDF, RAW, fonts: M3.
