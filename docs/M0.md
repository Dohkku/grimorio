# M0: measurements and decisions

Date: August 25, 2026
Machine: Ubuntu 24.04, 16 cores, 31 GB of RAM, NVMe, NVIDIA RTX 5060 Ti, X11.

Goal of the milestone: get the core working from the CLI and **choose the
toolkit with numbers**, without relying on opinions.

## What was measured and how

A synthetic library of 100,000 items (`grim synth`), with 512 distinct images
spread among them. Each item has its real `item.json`, its real thumbnail in the
pack and its real row in the index.

What the generator does **not** do: write the originals. It measures what the
interface touches (index, pack, JSON), and leaves import out. That is what
`grim bench import` is for: it does generate real images and imports them.

## Core

Generating the 100,000-item library, 31 s in total:

| Phase | Time | Rate |
|---|---|---|
| 512 distinct images + thumbnails | 2.0 s | 49,184/s |
| Metadata in memory | 18 ms | — |
| 100,000 `item.json` to disk | 8.0 s | 12,433/s |
| Thumbnail pack (405 MB) | 10.9 s | 9,175/s |
| SQLite index (with FTS and tags) | 9.6 s | 10,410/s |

Full rebuild of the index from disk (`grim bench reindex`): 100,000 items in
**12.2 s**, 8,175/s. That number is the price of the promise that
`index.sqlite` is disposable.

Real import, 600 JPEGs of 3000×2250 (1.8 GB): **63.7 img/s, 15 ms per image**.
Budget: > 20 img/s. And that is without libvips yet; downscaling while loading
should bring that number down quite a bit.

Queries over 100,000 items, 100 repetitions:

| Query | p50 | p95 | Budget |
|---|---|---|---|
| First page (200) | 0.15 ms | 0.23 ms | 16 ms |
| Page 50 (offset 10,000) | 2.09 ms | 4.31 ms | 16 ms |
| Text «textura» | 10.43 ms | 11.33 ms | 30 ms |

| Accent-insensitive: «tipografia» | 14.99 ms | 17.50 ms | 30 ms |

Everything is within budget, but the text searches (10-17 ms) and the color one
(24 ms) have less headroom than I would like. They are the first candidates for
optimization in M2.

## Grid on the GPU

`spikes/grid-wgpu`: 100,000 thumbnails, an automatic back-and-forth pass over
the whole library, which forces continuous loading and eviction in the atlas.

| | With vsync (180 Hz display) | Without vsync (real ceiling) |
|---|---|---|
| Mean | 5.52 ms (181 fps) | 1.83 ms (545 fps) |
| p50 / p95 / p99 | 5.55 / 5.73 / 5.87 ms | 2.52 / 2.83 / 3.03 ms |
| Maximum | 28.3 ms | 5.46 ms |
| Frames > 16.6 ms | 0.09 % | 0 % |
| Own memory | **124 MB** | 141 MB |
| Thumbnails decoded | 49,374 in 12 s | 104,937 in 12 s |

First frame at **324 ms** from startup, with the 100,000-item library already
queried and the pack mapped.

### The two bugs the benchmark found

**1. 23 GB of resident memory.** The wish list asked for up to 256 thumbnails
per frame and the drawing thread only consumed 24. The channel between the
decoding threads and the drawing thread had no limit, so the difference (around
7,000 images per second, ~400 KB each) piled up in RAM. Fixed with a bounded
channel (the threads block instead of piling up) and by limiting the request to
the real consumption rate. Result: 23,684 MB → 124 MB, and along the way the p99
dropped from 31.8 ms to 5.87 ms, because work that was being thrown away
stopped being done.

**2. Permanent holes in the grid.** In-flight requests were kept in a set that
they only left when the image arrived. A request cancelled by scrolling never
arrives, so that item was never requested again. Fixed by storing the frame of
the request and expiring it after 30.

Both are design flaws in the pipeline, unrelated to the toolkit: they would show
up the same way in QML. Finding them now, in a 400-line spike, is exactly what
M0 was for.

### And a visual design flaw

In square grid mode the images were stretched to fill the square cell, instead
of being cropped around the center. You see it at once in a screenshot and
never in a test. Fixed with centered cropping in the texture coordinates.

## Toolkit decision

### The Qt Quick twin

`spikes/grid-qml` is the other half of the comparison: the same grid, the same
data, the same pass and the same metrics, written against Qt Quick instead of
wgpu.

So that the measurement compares toolkits and leaves JPEG decoders out of it,
both sides read through the same path:

- A C ABI bridge (`spikes/grid-qml/puente`) links `grimorio-core` statically
  and exposes the already resolved query. Not a single Rust type crosses the
  boundary: integers, pointers and bytes.
- `grim_thumb` returns a pointer **inside the memory-mapped pack**. Qt decodes
  from there with no intermediate copy, just like the wgpu pool.
- Decoding happens off the interface thread, in a
  `QQuickAsyncImageProvider` on Qt's global pool.
- Preloading is the same: a `cacheBuffer` of three quarters of a screen on each
  side.
- Frame time is taken in `frameSwapped`, on the render thread, which is the
  moment the image actually reaches the monitor.

The C boundary has five tests of its own, all about the only things that can
turn into a segmentation fault there: a null context, a path that is not a
library, out-of-range indexes, closing twice.

### What Ubuntu's Qt 6.4 does not ship

Two packaging findings that affect the decision, beyond this one machine:

1. **There is no `qsb` and no QtShaderTools.** Without them a `ShaderEffect`
   cannot be compiled, so the rounded corner SDF that the wgpu spike does in
   the shader cannot be replicated as is. The twin solves the corners with a
   nine-patch mask in a `BorderImage`: a single texture for the whole grid,
   correct as long as the background is flat. It works, but it makes clear
   that in Qt any custom effect depends on an extra tool.
2. **Debian's `qml6-module-*` packages do not declare their QML-level
   dependencies.** Installing `qt6-declarative-dev` and `qml6-module-qtquick`
   leaves the system without `QtQml`, `QtQml.WorkerScript` or `QtQuick.Window`,
   and `import QtQuick` fails at runtime with a message that does not say what
   to install. It is a distribution detail, but it is exactly the kind of thing
   that turns "install and go" into a lost afternoon for whoever downloads
   Grimorio. The seven packages needed are listed in
   `spikes/grid-qml/README.md`.

### The numbers, side by side

Same 100,000-item library, same 200 px square grid layout, same pass: the whole
library top to bottom and back in 12 seconds. `GridView` only does equal cells,
so the comparison uses the square grid, which is what both can do out of the
box.

| With vsync (180 Hz monitor) | wgpu | Qt Quick |
|---|---|---|
| mean | **5.51 ms** (181 fps) | 6.92 ms (144 fps) |
| p50 / p95 / p99 | **5.55 / 5.72 / 5.95 ms** | 6.81 / 8.66 / 9.84 ms |
| worst frame | 28.70 ms | **14.72 ms** |
| above 16.6 ms | 0.52 % | **0 %** |
| first frame | **259 ms** | 365 ms |
| own memory | 123 MB | 133 MB |
| thumbnails decoded | **49,757** | 74,707 |

| Without vsync, the real ceiling | wgpu | Qt Quick |
|---|---|---|
| mean | **1.71 ms** (586 fps) | 13.16 ms (76 fps) |
| p95 | **2.83 ms** | 18.58 ms |

And a third measurement that explains the other two: **with the grid nearly
still (200 items) QML hits exactly 5.56 ms / 180 fps**, the same as wgpu.

### What the numbers say

- **Drawing is not the problem.** With little to recycle, both toolkits stay
  locked to the monitor's refresh rate. QML's cost is in the churn: creating
  and destroying delegates, and uploading textures while the view moves.
- **QML does not drop below 60 fps even when pushed.** The worst frame of the
  whole pass was 14.72 ms, and the pass is far more brutal than any human
  scroll: the whole library twice in twelve seconds.
- **But QML has no headroom.** Without vsync it gets worse instead of better
  (13.16 ms against 6.92): its per-frame cost is CPU, and once the monitor's
  brake is released the interface and render threads take room away from the
  decoding ones. wgpu, on the other hand, has 4× of unused headroom.
- **Qt recycles thumbnails worse**: 74,707 decodes against 49,757 to cover the
  same ground. The custom atlas with LRU eviction hits 75 % of the time; Qt's
  pixmap cache, 63 %. Raising `QML_PIXMAP_CACHE_LIMIT` to 512 MB changed
  nothing.
- **Memory is a tie**: 133 MB against 123 MB. It is an argument for neither.
- **Style as data works in both.** The same `temas/papel.json` changes the look
  of both grids without recompiling, and both have their sentinel that fails if
  a hand-written color shows up.

Two details from along the way that apply to the product: moving the hover
highlight and the selection ring into a `Loader` (they exist only when needed,
instead of being two invisible nodes per cell) went from 136 to 144 fps; and
screenshots of the same frame in both engines are indistinguishable pixel for
pixel except for the antialiasing of the corners.

### The decision

**Qt Quick for everything, with the grid behind a narrow interface.**

QML handles the worst case without dropping below 60 fps and ties on memory. In
return it brings what would take years to write: text layout, input, IME,
accessibility, native dialogs, drag and drop, and a JavaScript engine that is
exactly what plugins need. Paying 25 % of frame time for that is a good deal.

The wgpu spike is not thrown away: it sets the bar and leaves plan B written
down. The grid talks to the rest only through a model and an image provider, so
replacing it with a `QQuickItem` with its own scene graph node (the same atlas,
the same pipeline) touches one file and no other.

The triggers for doing it, written now so they are not argued about later:

- the worst frame goes over 16.6 ms on a reasonable machine,
- thumbnails above 320 px or 4K displays with large cells,
- or profiling points at texture uploads rather than decoding.

## Fourth pass: the slowest query in the program

When the test library was regenerated, the color search went over budget: a p95
of 31.9 ms against a target of 30. The benchmark failed, which is what it is
there for.

Measured before touching anything, the SQL cost 6.4 ms of the 32. The other 25
were in the comparator: `sort_by` called `color_distance` on every comparison,
and sorting 1,600 candidates means some 34,000 conversions to Oklab (three
`powf` and three `cbrt` each) for 1,600 distinct values.

The fix is textbook and worth writing down: compute the distance once per
candidate, pick out the best ones with `select_nth_unstable_by` (linear) and
sort only those. Along the way, compare the squared distance: the square root
is monotonic and sorting does not need it.

| color search, p95 | before | now |
|---|---|---|
| `#1f6b72` over 100,000 items | 31.9 ms | 22.5 ms |

Three new tests pin down the behavior as well as the speed: the order goes from
near to far, an item with no palette goes to the end but does not disappear, and
asking for more results than there are does not blow up.

## State of the code

- `grimorio-core`: library, index, search, import (copy/move/reference),
  thumbnails, palette, perceptual hash, index rebuild.
- `grim`: `init`, `import`, `ls`, `search`, `show`, `tag`, `star`, `stats`,
  `reindex`, `synth`, `bench`.
- `grid-spike`: virtualized grid, atlas with LRU eviction, decoding with
  viewport priority and cancellation, two layouts, theme in JSON, windowless
  capture mode.
- `grid-qml`: the same benchmark against Qt Quick, with a C ABI bridge over the
  core, an asynchronous image provider over the mapped pack and the same
  `tema.json`. Measured; it is the one that decides the toolkit.
- 66 tests (44 for the core, 4 for the CLI, 13 for the wgpu spike, 5 for the C
  bridge and 2 for QML), all green, and none needs a desktop except the QML
  ones, which only read files.
